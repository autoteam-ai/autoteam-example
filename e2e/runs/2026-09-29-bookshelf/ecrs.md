# autoteam 流程的 ECRS 优化

用流程优化的 ECRS 方法，把 autoteam 的三条流程（接入、交付、运营）逐步过一遍：先问这一步能不能**取消**（Eliminate），不能取消的能不能**合并**（Combine），再看顺序能不能**重排**（Rearrange），最后才**简化**（Simplify）剩下的步骤。

依据有三份，都能在本目录或 autoteam 仓库里复核：

- 这一轮书架示例：一个两批需求，17 次 agent 运行（[evidence/](evidence/) 里的运行记录，含耗时和 token）；
- autoteam 自举工作区 hdgcs 最近 10 天：推进巡检 56 次、部署结果 76 次、各报告类 autopilot 的运行记录；
- autoteam main 的角色指令、autopilot runbook 和文档。

逐条的问题描述在 [improvements.md](improvements.md)，这里按流程重新整理，编号 `#n` 指向那里。

## 结论

**浪费主要不在写代码，在协调。** 一个两批需求里，Planner 跑了 13 次、输出 7.3 万 token；两个 Implementer 一共 2 次、1.6 万 token，Reviewer 2 次、0.6 万 token。协调和生产的比例是 4.6 : 1，而且 Planner 用的是最贵的模型。

| 浪费 | 数据 |
|---|---|
| Planner 的运行里没有产出的 | 13 次里 6 次（占它 37% 的 token、34% 的时间） |
| 推进巡检空跑 | 自举工作区 33 次完成的巡检里约 21 次「本轮无事可做」（64%），另有 14 次被平台跳过 |
| 部署结果重复验收同一个任务 | 70 次里 22 次在复查同一个观察期任务 HDGCS-89 |
| 运行失败的原因 | 绝大多数是 Claude 会话额度用完，而 Planner 和巡检、部署结果都跑在这份额度上 |

协调开销和开发抢的是同一份订阅额度，所以**砍协调开销就是直接提高交付吞吐**。最值得先做的五件事：

1. 修掉阻塞 bug：普通项目缺 `./autoteam`（#11），`pipefail` 加 `grep -q` 偶发失败（#1）；
2. 在唤醒 LLM 之前先用脚本判断「有没有事」：巡检和部署结果没事就不唤醒 Planner（E1、E2、R1）；
3. 父任务整体验收只留一个入口，每个动作做成幂等的（E6、C1）；
4. 部署结果只验收这次部署新合进来的任务，观察期任务改用定时唤醒（E7）；
5. 派发不再每次跑完整 `autoteam doctor`（E5）。

| 07:39 | 人回复 | 拆分成两批 | **是** |
| 07:40 | 建「运营笔记」 | 自己建的任务指派给自己，又把自己叫醒 | 否：自触发 |

| 07:55 | 批次屏障 | 派发 AUTO-4（输出 1.3 万 token） | **是**（偏重） |

人在交付里的动作：提需求、提一处修改、逐个把两个子任务改成 `todo`，还要按文档逐个核对 Planner 有没有被唤醒（界面批准偶尔不唤醒，`lifecycle.md` 里记着原因未明）。

### 1.2 运营：一直在跑的部分

| autopilot | 自举工作区 10 天的运行 | 观察 |
|---|---|---|
| 部署结果 | 76 次 | 有产出，但 22 次在复查同一个观察期任务 |
| 推进巡检 | 56 次 | 约 64% 空跑；每次都要先加载 Planner 的全部指令，部分运行还跑完整 doctor |
| 每日摘要 | 10 次 | 3 次失败 |
| 整合审计、agent 成绩单、规则复盘、前沿扫描 | 各 2～3 次 | 每份都是「出报告 → Planner 拆任务 → 人看」 |
| 路线图对账 | 1 次 | |
| 规格对账、老代码巡检 | 0 次 | 装了，从没跑过 |

新项目一接入就是 10 个 autopilot，doctor 要逐个检查，预览要逐个列出，人要逐个理解。

### 1.3 接入：一次性的

| 步骤 | 人要做的 |
|---|---|
| 建 3 个 GitHub App | 每个 7 步手工操作（权限、安装、下载私钥），共 21 步 |
| 放私钥 | 每台 agent 机器各放一遍，每个 clone 各跑一次 `--setup-git` |
| 生成和适配 | `init`，改 Makefile、3 个工作流、registry、conf、AGENTS.md |
| 配置平台 | `github` 预览 → `github --apply` → `multica` 预览 → `multica --apply` → `doctor` |
| 第一次演练 | 提需求；逐个批准并核对唤醒 |

这一轮接入花了约 15 分钟（操作者熟悉 autoteam），而 doctor 全绿之后，第一个需求仍然立刻卡住（#11）。

## 2. ECRS

### E 取消：去掉不产生价值的步骤

| # | 取消什么 | 依据 | 怎么做 | 对应 |
|---|---|---|---|---|
| E1 | 空巡检 | 自举 64% 空跑；本轮 08:00 空跑 | 巡检先跑脚本判断五类事（可派发的 todo、失败或卡住、shipping 超时、PR 待补救、打转到上限），一件都没有就不唤醒 Planner。见 R1 | — |
| E2 | 没有待验收任务时的部署通知 | 本轮 07:37；自举约 5 次 | 同一个脚本：这次部署没有 shipping 任务，也没动规则文件，就不唤醒 | — |
| E3 | 批准后续批次时的空唤醒 | 本轮 07:46 AUTO-4 | 后续批次的放行一律 `--no-start`；由批次屏障去叫醒 Planner（见 S3） | #14 |
| E4 | 「运营笔记」自己叫醒自己 | 本轮 07:40 | 由 `autoteam multica --apply` 在接入时建好（`stop` 本来也依赖它存在），Planner 不再现建 | — |
| E5 | 每次派发都跑完整 `autoteam doctor` | planner.md「派发」第 1 步；本轮派发评论里都写着「doctor 全部通过」 | 派发只看这两个 agent：runtime 在线、最近一次运行没因额度或登录失败。完整 doctor 只在接入、升级、部署了规则文件改动时跑 | — |
| E6 | 重复的父任务整体验收 | 本轮 08:02 和 08:03 各做一次，后一次输出 1.8 万 token | 整体验收只在批次屏障唤醒时做；部署结果只验收子任务（另见 C1 的幂等） | #15 |
| E7 | 每次部署都复查观察期任务 | 自举 70 次部署结果里 22 次提到 HDGCS-89 | 部署结果只验收「这次部署新合进来的 PR」对应的任务，不是「合并提交在 sha 里」的全部 shipping 任务；需要观察期、攒样本的验收，由 Planner 设一个到期的任务级 wakeup rule | — |
| E8 | 人逐个核对「批准后 Planner 醒没醒」 | first-run.md 第 3 步；lifecycle.md 记着界面批准偶尔不唤醒 | 用 S3 的一次批准命令代替界面拖卡片；巡检兜底 todo 任务 | — |
| E9 | 新项目默认装满 10 个 autopilot | 规格对账、老代码巡检 10 天 0 次，路线图对账 1 次 | 默认只开部署结果、推进巡检、每日摘要、规则复盘和合并后的周度健康报告（C2），其余在 `autoteam.conf` 里显式打开 | #7 |

### C 合并：把分散在几处的同一件事并起来

| # | 合并什么 | 依据 | 怎么做 | 对应 |
|---|---|---|---|---|
| C1 | Planner 的三个入口：部署结果、推进巡检、批次屏障唤醒 | 三处都可能派发、验收、做父任务验收，规则分散在三份文本里，本轮出现了重复验收和前后说法不一 | 三个入口都调用同一份「推进」runbook，只是带不同的事件。每个动作先查是否已经做过（已有【验收通过】评论、已指派 Implementer），做过就跳过 | #14 #15 |
| C2 | 6 份报告类 autopilot | 结构完全一样：出报告 → @Planner 拆任务 → 人看；按模板默认频率，人每周要读 5 份报告 | 整合审计、agent 成绩单、老代码巡检、规格对账并成 Auditor 的「周度健康报告」；前沿扫描、路线图对账并成「月度方向报告」；规则复盘保留（它针对的是人工介入） | — |
| C3 | 接入的五条命令 | `github` 预览/应用、`multica` 预览/应用、`doctor` | `autoteam setup`：一次预览 GitHub 和 Multica 的全部改动，确认一次，apply 完自动跑 doctor | — |
| C4 | 逐个批准子任务 | 本轮人改了 2 次状态；拆得越细改得越多 | 批准父任务 = 批准整个拆分方案（见 S3）；只想先做一部分时，才逐个批准 | — |

### R 重排：把便宜、确定的判断放到前面

| # | 重排什么 | 依据 | 怎么做 | 对应 |
|---|---|---|---|---|
| R1 | 先判断再唤醒 | 暂停检查、有没有事、是否已验收，都是确定性判断，现在却要先唤醒最贵的模型、加载 214 行指令之后才判断 | `autoteam next --check`（纯脚本）输出这一轮要做的事；巡检和部署结果的第一步只执行它给出的清单，清单为空就直接结束。更进一步：巡检的定时放到 GitHub Actions，有事才调 Multica webhook | #11 |
| R2 | 模拟一次 agent 开工，放进接入阶段 | doctor 全绿，第一个需求却卡在 `./autoteam` | doctor 在一个干净的 checkout 里跑一遍 `bash ./autoteam status --check`，把 agent 真正会跑的命令提前跑一次 | #11 |
| R3 | 「部署等线上生效」放到通知之前 | 推完就通知的话，Planner 可能验收到旧版本 | 写进 `make deploy` 的适配原则和 deploy.yml 模板注释：先等线上 `version`/`healthz` 返回这次的 sha，再通知 | #6 |
| R4 | 语言在接入时定一次 | Planner 第一条评论是英文，Codex 的提交信息是英文 | `autoteam.conf` 加 `AUTOTEAM_LANGUAGE`，前言里统一要求 | #12 |
| R5 | 能不能共用工作区，在预览时就告诉用户 | 同一工作区第二个项目 apply 会改掉别人的 autopilot | 预览时发现同名 autopilot 绑在别的项目上就报 ❌，并提示新建工作区；或者按 `(title, project_id)` 匹配 | #2 |

### S 简化：剩下的步骤做得更轻

| # | 简化什么 | 依据 | 怎么做 | 对应 |
|---|---|---|---|---|
| S1 | Planner 的指令 | 214 行，占四个角色指令的 59%；每次运行不论做什么都全量加载；#14 就是一条规则写在了别的章节里被误读 | 角色指令只留身份、原则和「你不能」；拆分、派发、验收、换人、升级各自成一份 runbook，按触发事件只加载需要的那份 | #14 |
| S2 | 建 GitHub App | 21 步手工操作 | 用 GitHub App Manifest：`autoteam github --create-apps` 生成三个带预填权限的链接，人各点一次确认，私钥自动落到 `AUTOTEAM_KEYS_DIR` | — |
| S3 | 人的批准 | 逐个改状态，还要核对唤醒 | `autoteam approve <父任务>`：第一个可派发的批次正常唤醒，后续批次 `--no-start`，输出每个任务的放行结果 | #14 |
| S4 | 人改规则文件 | 要懂 App token、凭据助手，本轮走了三次 | `autoteam propose`：当前改动用 Implementer App 开 PR，人只批准 | #13 |
| S5 | 缺失的入口文件和 skill 目录 | 接入后要人自己补 | `init` 生成 `./autoteam`（固定版本，`upgrade` 负责更新）；`.gitignore` 受管块加上 `.claude/skills/` | #11 #3 |
| S6 | 命令输出 | 只有 ID 没有链接；doctor 同一台机器报 6 行；stop 预览列两遍 | 输出 Multica 网页链接；按机器聚合；只列一遍；stop 说明暂停期间的部署通知会丢 | #8 #9 #16 #17 |
| S7 | 错误信息 | 「没登录」和「没配置」报同一句；14% 的偶发误报 | 修掉 `pipefail` 加 `grep -q`；两种情况分开报 | #1 #10 |
| S8 | 模板里的遗留 | PR 标题例子还是「按日期导出订单」 | 换成中性例子 | #5 |
| S9 | 用量口径 | 挂在 autopilot 名下的运行不算进任何任务 | 摘要和成绩单按 agent 汇总，单列 autopilot 的用量 | #18 |

## 3. 优化后的样子

同样一个两批需求：

| | 现在 | 优化后 |
|---|---|---|
| 人的动作 | 提需求、逐个批准 2 次、逐个核对唤醒 | 提需求、`autoteam approve` 一次 |
| Planner 运行 | 13 次（6 次无产出） | 约 6 次：拆分、（按需）改描述、派发第 1 批、验收第 1 批、派发第 2 批、验收第 2 批并整体验收 |
| Planner 输出 token | 7.3 万 | 约 4.6 万（去掉无产出的 2.7 万，即 37%）；每次运行不再跑完整 doctor、只加载相关的 runbook，实际更低 |

持续运行的部分：

| | 现在 | 优化后 |
|---|---|---|
| 推进巡检 | 每 2 小时唤醒一次 Planner，约 64% 空跑 | 脚本先判断，有事才唤醒 |
| 部署结果 | 每次部署都唤醒；观察期任务反复重验 | 只在有新合入的待验收任务时唤醒；观察期任务到期才验 |
| 默认 autopilot | 10 个 | 5 个（部署结果、推进巡检、每日摘要、规则复盘、周度健康报告），其余按需打开 |
| 人要读的报告 | 按默认频率每周 5 份、每月 1 份，外加每天的摘要 | 每周 2 份（健康报告、规则复盘）、每月 1 份（方向），外加每天的摘要 |

接入：

| | 现在 | 优化后 |
|---|---|---|
| 建 App | 21 步手工 | 3 次点击 |
| 配置命令 | `github` ×2、`multica` ×2、`doctor` | `autoteam setup` 一次确认 |
| 接入后第一个需求 | 卡在 `./autoteam` | doctor 已模拟过 agent 开工 |

## 4. 落地顺序

| 优先级 | 内容 | 为什么先做 |
|---|---|---|
| P0 | #11（`./autoteam`）、#1（偶发误报）、E6（重复验收） | 前两个让新用户第一天就卡住；E6 是单次最大的浪费 |
| P1 | R1 + E1 + E2（先判断再唤醒）、E7（只验新合入的任务）、E5（派发不跑完整 doctor）、S3（一次批准） | 直接减少 Planner 的运行次数和额度占用，收益最大、改动集中在脚本和 runbook |
| P2 | S1（拆 Planner 指令）、C1（统一入口 + 幂等）、C2 + E9（报告合并、默认少装） | 结构性调整，需要重新验证一轮 |
| P3 | C3 + S2（`setup`、App Manifest）、S4（`propose`）、输出和文案类（S6～S9、R4、R5） | 改善体验，不影响正确性 |

其中只有「界面批准偶尔不唤醒」「暂停的 autopilot 仍显示下次运行时间」需要 Multica 那边改，其余都能在 autoteam 里完成。

## 5. 不建议动的

ECRS 容易把「看起来多余」的闸门也砍掉。下面这些步骤看起来是开销，其实是 autoteam 的安全边界，保留：

- **写代码和评审用两个不同的 App 身份**：平台保证作者不能批准自己的 PR，这是不变量，合并 App 省不了多少事，却会失去它。
- **新项目默认由人批准**（`AUTOTEAM_AUTO_APPROVE=off`）：可以把批准变成一次（S3），但不要默认取消。
- **`shipping` 状态**：部署通知和巡检都靠它找「已合并、等验收」的任务。
- **规则集、合并队列、CODEOWNERS**：本轮 PR #15、#18 为此多走了「App 推、人批」的流程，该做的是把这条流程做成一条命令（S4），不是放宽闸门。
- **线上验收**：本轮 Planner 数了 102 个链接、核对 sha，这是整个流程里最能发现真实问题的一步，要省的是重复验收（E6、E7），不是验收本身。
